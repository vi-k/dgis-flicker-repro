# Состояние работы

Обновлено 27.08.2026.

## Зачем это всё

Приложение воспроизводит дефект 2GIS Mobile SDK для передачи вендору. Исходная
задача — [TT-2359](https://teztaxi.atlassian.net/browse/TT-2359) в
tez-taxi-monorepo: у пользователей моргала и пропадала машина на карте во время
поездки. У себя закрыто обходом (частота записи угла срезана до 5/с), но это не
исправление — приложению естественно писать направление на каждом кадре
анимации.

## Что доказано

**Условие дефекта — частая запись `iconMapDirection` с изменившимся значением.**

Оба слова важны:

- запись того же значения движок пропускает, переукладки иконки не происходит,
  и симптома нет ни при какой частоте;
- порог по частоте лежит между 20 записями в секунду (за три минуты чисто) и 60
  (постоянные пропажи).

Во время пропажи карта, дороги, подписи и полилиния маршрута рисуются нормально
— отсутствует только маркер. Кадры-улики лежат вне репозитория, см. ниже.

**На SDK 14.0.0 дефект тоже воспроизводится** (проверено 27.08 на Redmi).
Подтверждён покадрово дважды, в двух независимых прогонах: карта, подписи и
полилиния нарисованы, отсутствует только маркер, самый короткий эпизод — ровно
один кадр. Апгрейд SDK задачу не закрывает, обращение нужно.

Но на 14.0.0 симптом заметно реже: 33 эпизода за три минуты на 13.7.0 против
1, 0 и 2 в трёх прогонах на 14.0.0. Показательнее прочих последний — там размер
маркера уравнен с 13.7.0, значит у счётчика та же чувствительность. Все эпизоды
на 14.0.0 проверены покадрово; 33 — сырой счёт с артефактами.

**В 14.0.0 не действует `MarkerOptions.iconWidth`.** Иконка рисуется в размер
битмапа, истолкованный как логические пиксели. Доказано опытом: меняли только
размер растра, `iconWidth` не трогали — размер поехал за растром.

| Версия | Растр | `iconWidth` | Ширина на экране |
|---|---|---|---|
| 13.7.0 | 173 px | `LogicalPixel(63)` | 135 px |
| 14.0.0 | 173 px | `LogicalPixel(63)` | 385 px |
| 14.0.0 | 63 px | `LogicalPixel(63)` | 132 px |

Отсюда огромный маркер на всех записях 14.0.0, снятых со штатным кодом:
приложение растеризует в `63 × dpr = 173`, а 14.0.0 считает эти 173 логическими.
Обойти можно только растеризацией без dpr, но тогда иконка мылит.

Регресс недокументированный: сам пакет 14.0.0 описывает поле как «Целевая
ширина, используемая для масштабирования», а в changelog 14.0.0 изменений его
поведения не заявлено.

**Место расхождения в коде SDK найдено** — `lib/src/widgets/map/map_widget.dart`,
`_initialize()`. В 13.7.0 плотность экрана шла в `MapBuilder().apply(...)`, то
есть в создание карты. В 14.0.0 карту создаёт конструктор `MapWidgetController`
через `MapController.create(sdkContext, controllerOptions)`, а плотность виджет
навешивает после, через `map.camera.setDevicePpi(...)`. Полей плотности в
`MapControllerOptions` нет вовсе — на момент создания карты она неизвестна.

Измерения и список проверенного-и-неважного — в `README.md`, текст для вендора —
в `docs/issue-2gis.md`. Changelog SDK:
<https://docs.2gis.com/flutter/sdk/releases/latest> — 13.7.0 вышла 11.08.2026,
14.0.0 через пять дней, 16.08; промежуточных версий между ними нет.

## Чего НЕ доказано

- **`erasedPart` сама по себе полилинию не роняет.** На 60 записей в секунду за
  три минуты — ноль пропаж. Ранний вывод об обратном был ошибкой: он пришёл из
  прогона, где вдобавок работало пересоздание маршрута.
- **Пропажа обоих объектов разом** наблюдалась только когда обе записи идут на
  60/с. При записи одного лишь направления линия остаётся целой.
- **Редкие кадры с пустой картой целиком** (пропадают и тайлы, и подписи)
  встречались несколько раз, примерно раз в девять минут. Отдельное явление,
  не разобрано, в обращение не вошло.
- **Во сколько раз 14.0.0 реже — точно неизвестно.** Порядок величины разницы
  сомнений не вызывает, но 33 для 13.7.0 — сырой счёт, покадрово он не отобран,
  а по опыту больше половины таких провалов оказываются артефактами.
- **Почему на 14.0.0 реже — не разобрано.** Есть две правдоподобные версии, и
  выбрать между ними нечем. Первая: в changelog 14.0.0 значатся исправления
  «фризы маркеров» и «исчезновение тайлов пробок, маркеры с `visible = false`» —
  возможно, наш симптом задет ими частично. Вторая: версии рисуют разный объём
  содержимого, потому что подписи и объекты карты на 14.0.0 крупнее и в кадр при
  том же `Zoom(16)` попадает меньшая площадь.

## Грабли инструментов

Первые две стоили по несколько часов и обе давали правдоподобный, но ложный
результат.

- **`ffmpeg -ss` до `-i`** — быстрый поиск по ключевым кадрам: отдаёт не тот
  кадр, а иногда мусорный, декодированный без опорных. Проверять кадры только
  по точному номеру: `-vf "select=eq(n\,N)" -fps_mode passthrough`.
- **`screenrecord` пишет с переменной частотой.** Без `-fps_mode passthrough`
  ffmpeg приводит её к средней, выбрасывая кадры: номера расходятся с файлом, а
  короткий эпизод теряется целиком. В `tools/darkcount.py` это учтено.
- Правило, выведенное дорогой ценой: **любой найденный провал проверять
  кадром**, прежде чем делать вывод. Из проверенных так провалов больше половины
  оказались артефактами — то камера уводила объект за край, то трасса
  заворачивалась, то объект уходил под шторку.
- **Две правдоподобные версии про масштаб проверены и опровергнуты.** Первая:
  плотность применяется дважды — тогда `MapWidgetOptions.deviceDensity: 1.0`
  вернул бы прежний масштаб. Не вернул, картинка не изменилась совсем. Вторая:
  опция вообще инертна — тогда и крайнее значение ничего бы не дало. Дало: при
  плотности 10 маркер уменьшается, охват карты не меняется, время растра растёт
  с 12.9 до 36.9 мс, кадры падают с 27 до 14 в секунду. Похоже, плотность
  управляет разрешением внутреннего буфера, а не логическим масштабом, но
  дальше начинается нативный код, и проверить это нечем.
- **Сырой вывод `darkcount.py` — не то же, что числа в `README.md`.** Скрипт на
  `evidence/marker-hi1.mp4` даёт 22 провала, тогда как в таблице стоит 38: в
  таблицу попали числа после отбора кадрами, а сырой счёт включает артефакты.
  Сравнивать между собой можно только прогоны, обработанные одинаково; с
  таблицей — нельзя.

| Vivo V2310, Android 14 (устройство QA) | `kz.nidge.tez_taxi.tez_taxi.stage` | stage | стоит репро; stage-клиент снесён, рядом стоит dev-клиент |

Vivo на 27.08 с сети ушёл — подключать заново, проще кабелем. Redmi на 27.08
подключён по Wi-Fi (`adb connect 192.168.14.170:5555`); режим держится до
перезагрузки или потери сети.

На Redmi на 27.08 стоит чистая сборка ветки `sdk-14` (14.0.0, коммит с темой),
поставлена в 12:56 — маркер на ней огромный, и это ожидаемое поведение версии,
а не испорченная сборка. Все временные сборки опытов (`Zoom(14.54)`, растр
иконки без dpr, `deviceDensity` 1 и 10) откачены и на устройстве не стоят.

Экран на устройстве не гаснет: включён `adb shell svc power stayon true`.
Вернуть обычное поведение — `adb shell svc power stayon false`.

Ключ 2GIS проверяет идентификатор приложения, поэтому репро собирается под
занятый app id:

```bash
REPRO_APP_ID=kz.nidge.tez_taxi.tez_taxi.dev \
  flutter build apk --release --target-platform android-arm64
```

Ключ кладётся в `assets/dgissdk.key` (в репозиторий не входит), берётся из
`apps/client/assets/gis_keys/<flavor>/dgissdk.key` монорепо.

## Что осталось

1. Отправить `docs/issue-2gis.md` в 2GIS. Публичного трекера у Flutter SDK нет,
   канал — личный кабинет или почта.
2. По желанию — добить редкие кадры с пустой картой целиком.
   Смежное: в changelog 14.0.0 есть «исчезновение тайлов пробок» — возможно,
   та же природа.
3. По желанию — довести уравнивание масштаба, если понадобится честное
   отношение частот между версиями.

входят (гигабайты видео). Ключевые пары «до/после»: пропажа маркера при
`iconMapDirection` 60/с и пустая карта целиком.
